# Online own-post retrieval: bounded compatibility check

Checked on 2026-11-07 against the signed-in X web client. This is a feasibility report; My Posts remains an archive-import feature in this change.

## Observed

- The account's own Profile link was obtained from the signed-in navigation. Requests were generated by ordinary X page navigation and one scroll, with network responses inspected read-only.
- The current **Posts** tab uses GraphQL operation `UserOriginalsTimeline`, rather than assuming the older `UserTweets` operation name.
- The first Posts response returned HTTP 200. It contained 27 unique Tweet objects, 27 `full_text` fields, four long-note text fields, a `TimelinePinEntry` instruction, and nonempty Top/Bottom cursors.
- One scroll requested a second `UserOriginalsTimeline` page with a cursor. It returned HTTP 200 and 25 unique Tweet objects, of which 23 were new relative to the first response. The response contained 26 full-text instances and seven long-note text instances; duplicate/nested objects explain why instance and unique-ID counts differ.
- The **Replies** tab uses `UserRepliesTimeline`. Its initial response returned HTTP 200 with 41 unique Tweet objects, 21 reply-relation field instances, 41 full-text instances, and five long-note text instances.
- Long text appeared under `note_tweet.note_tweet_results.result.text`; legacy text appeared under `legacy.full_text`. A collector should prefer the long-note text when present.

These object counts include nested quoted posts and conversation context. They are response-shape evidence, not counts of posts authored by the account. The timeline envelope did not expose the owner's ID at `data.user.result.rest_id`; future collection must establish the account's stable ID separately and filter each top-level item's author/repost relationship explicitly.

The check stopped after two Posts responses and one Replies response. It restored the original Home page and disabled network observation. It performed no post, mute, follow, or account-setting mutations. No credentials, account identifiers, post text, raw response bodies, request URLs, or cursor values were written to this repository.

## Feasibility and limits

Recent online paging is feasible in the current signed-in web session: the native site supplied a next-page cursor and successfully used it to return additional content. This check did not replay requests from extension code, establish the required request metadata independently, test a separate login state, or determine the oldest reachable date. GraphQL operation identifiers and feature arguments remain a version-dependent integration detail.

The official API documents a 3,200-most-recent-post limit for the user timeline. X's help page also describes profile display limits and older posts missing from search/timelines due to indexing restrictions. These limits are reasons to retain official archive import as the historical-data path; a few successful pages do not prove complete historical coverage.

## Follow-up implementation boundary

Use a dedicated read-only adapter for Posts and Replies, with current-account validation and explicit item normalization. Store each page and its next cursor together, deduplicate by string post ID, and retain source/coverage metadata. Treat pinned entries, conversation modules, nested quotes, repeated cursors, empty pages, session changes, and rate limits explicitly. Report the observed time coverage; completion of a pagination run is distinct from proof that every historical post was returned.

The existing muted-word bridge is restricted to four fixed keyword endpoints and remains dedicated to that feature. Online collection can reuse the background task's pause/resume principles after the adapter is separately implemented and tested.
